## 本次实测结论（2026-10）

1. **瓶颈定位：题面解析与规则兜底层，而非符号计算内核**。同一台 SymPy 服务，经本评测的
   LaTeX→SymPy 转换器（策略 A）21/21 全对；经多智能体端点（策略 B）0/27。
   B 的 solver 本地计算路径无法消化基准集的 LaTeX 题面，全部跌出到规则引擎兜底。
2. **B 的 27 个回答全部是不可用输出**：8 题返回显式占位"未能得出确定结果"；
   19 题返回"已整理结论"这类无信息泛化文本（未被占位检测覆盖，应纳入）；
   个别题给出错误具体答案（如链式法则半成品 `\cos(5x) · (5x)'`）。
3. **编排开销显著**：B 均耗 4018ms ≈ A（35ms）的 115 倍——四智能体串行编排 +
   规则兜底路径的固定成本。若题面解析修复到 A 的水平，B 的增量价值需用
   "步骤质量/诊断覆盖"重新衡量，而非仅看答案正确率。
4. **行动项（按优先级）**：
   - 把 `scripts/latex-to-sympy.cjs` 的转换能力移植进 solver 的本地计算路径（或让
     solver 直接复用该转换逻辑），消除 LaTeX 题面的解析缺口（P1）；
   - "已整理结论"等无信息泛化文本纳入 `isPlaceholderResult` 检测（P1）；
   - 配置真实 LLM API key 后重跑本消融，测"符号优先 + LLM 兜底"的完整形态（P2）。

## 方法论说明

- 本评测为**真实对照实验**：两策略吃相同题面、用同一判定器、逐题原始数据落盘 `results/ablation-raw.json`。
- 若 B 显著低于 A，说明多智能体链路当前的主要瓶颈在题面解析/编排层而非符号计算内核；
  "退化为占位文本"计数直接暴露 LLM key 未配置或解析失败的题目数量。
- 若 B 与 A 相当，说明符号优先 + 规则兜底的降级设计在可用性上成立，延迟差即为编排开销。
- 重复运行 `node scripts/ablation-eval.cjs`（保持服务可用）应得到一致结论。
- 运行注意：后端 `/agents/*` 限流 20 次/5 分钟/IP，脚本默认 16s 请求间隔 + 429 指数退避，
  全程约 15 分钟；评测时 LLM key 未配置（环境本就如此，结果如实反映降级形态）。
