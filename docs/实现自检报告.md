## 一、逻辑与正确性

### ✅ 经实测确认正确（无问题）

| 项 | 实证结果 |
|---|---|
| refresh token 轮换 | `POST /auth/refresh` → 200，返回新令牌对 |
| 重用检测（重放攻击） | 旧值二次使用 → 401 `UNAUTHORIZED` |
| 登出吊销 | `POST /auth/logout` → 200 `{revoked:true}` |
| 统一错误信封 | 校验失败返回 `{code:"VALIDATION_ERROR",statusCode:400,message,traceId,timestamp}` |
| 登录失败锁定 | 连续错密码：401×5 → 429×2；锁定期间正确密码也 429 |
| 缓存 TTL 语义 | `RedisCacheService.set(key,val,ttlSeconds)` 确为秒，令牌 TTL 计算正确 |
| 密钥残留 | `secret-scan --scan` → 0 检出 |

### ❌ 发现的问题

**【P0-1】RBAC 完全失效：任何登录用户都能调用管理员接口**
- 位置：`core/auth/guards/roles.guard.ts`（**从未被注册**——不在任何 module providers、无 `@UseGuards`、非 `APP_GUARD`）；`modules/user/user.controller.ts:107/128/148`、`modules/problem/problem.controller.ts:23/40/47` 的 `@Roles('admin')`
- 实证：用刚注册的 **student** 账号，`GET /user/list` → **200**（返回全部用户列表）；`POST /user/create` → **201**（成功创建用户）
- 影响：`@Roles()` 目前是纯装饰性注解。学生可枚举全部用户、创建账号、删除账号。这与第一轮修掉的"注册即提权"是同一级别的越权，只是入口不同。

**【P0-2】`JwtStrategy` 丢弃 `roles`，接上 RolesGuard 后会反向变成全员 403**
- 位置：`core/auth/strategies/jwt.strategy.ts:30-33` —— `validate()` 只返回 `{userId, username}`
- `roles.guard.ts:23` 读的是 `request.user.roles`；`TokenService.signAccess` 确实把 roles 签进了 payload，但被 validate 丢弃
- 影响：与 P0-1 是**连环**问题——只修"注册守卫"会让所有带 `JwtAuthGuard` 的接口（包括 admin）一律 403；只修"补 roles"则仍然无人校验。两处必须一起改。
- 附带：`GlobalAuthGuard` 直接 `request.user = payload`（含 roles），与 `JwtStrategy` 的产物**结构不一致**（一个带 roles、一个不带），调用方行为取决于用了哪个守卫，属数据不一致。

**【P1-3】并发刷新会吊销用户的整个令牌族（可用性缺陷）**
- 位置：`core/auth/token.service.ts:125-164`（`rotate` 非原子：读记录 → 标 used → 删 → 签发）
- 实证：5 个请求并发用同一 refresh token → `200,401,401,401,401`；后续用新值续期 → **401**
- 影响：判定为泄露后吊销整族是安全上正确的，但**多标签页 / 多设备 / 小程序多实例**天然会并发刷新，结果是合法用户被踢下线。前端单飞只解决了单页面内的并发。

**【P1-4】15 分钟短时效的设计目标在实际运行中未生效**
- 位置：`nestjs-backend/.env`（`JWT_EXPIRATION=7d`）、`docker-compose.yml:126`（`JWT_EXPIRATION=${JWT_EXPIRATION:-7d}`）
- 实证：登录响应 `expires_in=604800`（7 天）、`refresh_expires_in=604800`
- 影响：代码默认 15m 只在**未配置**时生效，而所有运行环境都显式配了 7d。安全收益（泄露窗口 7 天→15 分钟）实际为零。

**【P1-5】登录失败会被前端误判为"会话过期"并强制登出**
- 位置：`uniapp-frontend/src/utils/request.ts:108-121`
- 逻辑：`POST /user/login` 密码错误返回 401 → 拦截器尝试 refresh → 若本地存在仍有效的旧 refreshToken 则刷新成功 → 重放登录请求仍 401 → `_retry` 已置位 → `forceLogout()` + toast「登录已过期」
- 影响：用户输入错误密码时，看不到"用户名或密码错误"，反而被清会话并踢到登录页。

**【P2-6】并发 401 会重复触发登出跳转**
- 位置：`request.ts:114-119`（每个并发失败请求各自 `forceLogout()`）
- 影响：一次过期引发 N 次 `reLaunch` + N 个 toast。

**【P2-7】非法 JSON 请求体 → `traceId: "unknown"`**
- 位置：`common/interceptors/trace-id.interceptor.ts`（拦截器在 body 解析之后才建立上下文）
- 实证：`{bad json` → 400，但 `traceId:"unknown"`，线上无法定位该请求。

**【P2-8】空密码触发"密码过长"的荒谬提示**
- 位置：`modules/user/dto/login.dto.ts`
- 实证：`{"username":""}` → message = `用户名不能为空; 密码过长; 密码长度至少 6 位; 密码不能为空; 密码必须是字符串`
- 原因：校验器未对空值短路，`@MaxLength` 对 `undefined` 也参与判定。

**【P2-9】登出只清 user store，其他 store 残留上一用户数据**
- 位置：`uniapp-frontend/src/stores/user.ts:111-133`
- 影响：登出/换账号后，错题本、学习记录等 store 仍持有旧用户数据（数据不一致）。

## 三、结构合理性

### ✅ 无问题的部分
- 分层清晰：`AuthController`（解析请求）→ `AuthService`（编排）→ `TokenService`（令牌与存储）职责单一，控制器不含业务逻辑。
- 错误体系与令牌体系各自成目录（`common/errors/`、`core/auth/`），命名一致。
- 复用了既有 `RedisCacheService`（含内存降级），未为限流/令牌另起一套缓存依赖。

### ❌ 问题

**【P2-14】会话清理逻辑重复**：`request.ts:34-38` 的 `clearSession()` 与 `stores/user.ts:126-131` 登出清存储是同一份逻辑的两份实现，改一处容易漏另一处。

**【P2-15】两套守卫并存导致 `req.user` 结构不一致**：`GlobalAuthGuard`（放 payload）vs `JwtStrategy`（放 `{userId,username}`），调用方拿到的用户对象形状取决于用了哪个守卫（详见 P0-2）。

**【P2-16】重复实现（既有债务，本轮未恶化也未收敛）**：两套前端、两份 SymPy 服务、三套公式渲染仍在仓库中。

## 四、可维护性

### ✅ 无问题的部分
- 关键设计取舍都有注释说明理由（为何锁账号不锁 IP、为何单飞、为何子进程跑 SymPy、为何多实例必须配 Redis）。
- 错误码表 + HTTP 状态映射集中管理，前端可按 `code` 做策略映射。
- 生产环境不回传堆栈与 `details` 已落地。

### ❌ 问题

**【P1-17】JWT payload 被整体打印进日志**
- 位置：`core/auth/strategies/jwt.strategy.ts:31` —— `logger.log('JWT payload validated: ' + JSON.stringify(payload))`
- 影响：**每个请求**都把用户身份信息写日志（噪音 + 凭据相关信息外泄）；应改 debug 且只打 username/userId。

**【P1-18】日志脱敏覆盖不全**
- 残留整体打印 error 对象的点：`modules/agents/agent.orchestrator.ts:152`（`logger.error('多智能体协作流程执行失败', error)`）、`modules/agents/planner/planner.agent.ts:80`（`logger.warn(..., error)`）
- 影响：这正是当初泄露 `Authorization` 头的同一类写法，axios 错误对象会带 `config.headers`——**泄露通道未完全堵住**。其余 40+ 处已改为 `error.message` 或 `describeErrorForLog`，风险较低。

**【P2-19】注释与实现不符的两处**
- `login-throttle.service.ts:61` 注释称"用 TTL 反推剩余锁定时间"，实际返回的是存储的固定 `lockSeconds`（不会随时间递减）。
- `token.service.ts` 注释称 refresh 30 天，代码默认 7 天（且未在任何配置中声明）。

**【P2-20】refresh token 存于 `uni.setStorageSync`**：小程序/App 端无 HttpOnly Cookie 可用，属平台限制下的折中，已记录；H5 独立部署时需迁移到 SameSite Cookie。

## 五、下一步完善计划（按优先级）

### 第一步（P0，必须最先做，且两处一起改）
**1. 让 RBAC 真正生效**
- 解决：P0-1 + P0-2（`@Roles` 无守卫执行 + `JwtStrategy` 丢弃 roles）
- 做法：① `JwtStrategy.validate()` 返回 `{ userId, username, roles }`；② 把 `RolesGuard` 注册为全局 `APP_GUARD`（放在 `GlobalAuthGuard` 之后），或至少在所有 `@Roles` 处显式 `@UseGuards(JwtAuthGuard, RolesGuard)`；③ 统一 `GlobalAuthGuard` 与 `JwtStrategy` 产出的 `req.user` 结构；④ 补一个"student 调 admin 接口必须 403"的集成测试作为回归防线。
- 预期效果：学生枚举用户/建号/删号的越权路径关闭，管理员功能恢复正常可用。
- 改动范围：`jwt.strategy.ts`、`roles.guard.ts`、`app.module.ts`（或各 controller 装饰器）+ 1 个新 spec。

### 第二步（P1，配置与安全目标落地）
**2. 让"15 分钟短时效"真正生效**
- 解决：P1-4 + P1-10
- 做法：`JWT_EXPIRATION=15m` 写入 `.env`、`.env.example`、`docker-compose`；新增并文档化 `JWT_REFRESH_TTL`（建议 30d）、`LOGIN_MAX_FAILURES/LOCK_SECONDS/WINDOW_SECONDS`；`env.validation.ts` 增加"生产环境 JWT_EXPIRATION 不得超过 1 小时"的硬校验（把注释承诺变成代码保证）。
- 预期效果：access token 泄露窗口从 7 天降到 15 分钟；配置可见、可调、可校验。
- 改动范围：3 个配置文件 + `env.validation.ts`。

**3. 堵住剩余日志泄露通道**
- 解决：P1-17 + P1-18
- 做法：`jwt.strategy.ts` 改为 debug 级且只打 userId/username；`agent.orchestrator.ts:152`、`planner.agent.ts:80` 改用 `describeErrorForLog(error)`；给 `secret-scan` 增加一条"禁止 `logger.*(..., error)` 整体打印对象"的静态检查（ESLint no-restricted-syntax 或简单 grep 门禁）。
- 预期效果：凭据不再进入日志，且有门禁防复发。
- 改动范围：3 个文件 + 扫描脚本增强。

**4. 并发刷新的可用性修复**
- 解决：P1-3
- 做法：为 refresh token 增加**重放宽容窗口**（如 30 秒内同一 token 的重复请求返回当前有效令牌而非判定泄露），或让 `rotate` 的"读-标记-删除"走 Redis Lua 脚本保证原子性；超出窗口仍吊销整族。
- 预期效果：多标签页/多设备不再被误判为令牌泄露，同时保留真实的重放攻击防护。
- 改动范围：`token.service.ts` + 补充并发场景单测。

**5. 前端登录/登出体验修正**
- 解决：P1-5 + P2-6
- 做法：登录、注册、刷新三类请求跳过 401 自动刷新（按 URL 白名单判断）；`forceLogout` 加"已登出"幂等标志避免重复跳转。
- 预期效果：密码错误显示"用户名或密码错误"而非被踢下线；过期时只跳转一次。
- 改动范围：`uniapp-frontend/src/utils/request.ts`。

### 第三步（P1/P2，一致性与工程债）
**6. 第二套前端去留决策**：`math-tutor-prototype` 要么同步认证改造（登录路由改 `/user/login`、接入 refresh、令牌移出 localStorage），要么明确废弃并从仓库移除（推荐后者，配合 P2-16 一并收敛）。
**7. 测试补齐**：`LoginThrottleService`、`AuthController`、`TraceIdInterceptor` 单测；把本轮两个探针（`.self-check/probe-rbac.cjs`、`probe-refresh.cjs`）固化为 CI 可用的集成测试。
**8. 自检流程修复**：`self-check` 必须**先重新编译 dist 再启动后端**（否则会重演"验证旧代码"）；同时修复其清理测试账号删除 0 条的缺陷。
**9. 细节修正**：空密码校验短路（P2-8）；`expires_in` 用于提前刷新或删除该注释（P2-12）；登出清理全局 store（P2-9）；抽取统一的会话清理工具（P2-14）；修正两处注释与实现不符（P2-19）。
