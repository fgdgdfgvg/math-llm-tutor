# Neo4j 知识图谱：取舍论证与现状核查

> 结论先行：**保留 Neo4j 作为"可选增强"，不把它放在核心解题链路上**。
> 当前图谱规模很小（种子 31 概念 / 39 关系），内存 fallback 完全够用；
> 保留图数据库的价值在于前置依赖链与学习路径规划的**表达能力上限**，
> 而非当前数据量。同时必须正视两个已核查的问题：实例数据与代码种子不同步、
> 旧数据标签 schema 不一致。

---

## 1. 它在系统里做什么

`KnowledgeService`（`nestjs-backend/src/modules/knowledge/knowledge.service.ts`）维护高数概念图谱：

- **节点**：数学概念（极限、导数、微分中值定理……），含难度、标签、公式；
- **关系**：`PREREQUISITE_OF`（前置依赖）等，支撑"想学 X 需要先学 Y"的学习路径规划；
- **消费者**：planner 智能体（按知识点检索相关概念注入解题上下文）、学习路径推荐。

**关键设计：可降级**。`waitForNeo4jAndInit`（knowledge.service.ts:49-77）启动时最多等 Neo4j 10 次（约 10s），
失败则用 `getDefaultMathConcepts()` 的 31 概念种子初始化内存图，功能不中断。
因此 Neo4j 不在 `/health/ready` 关键依赖里（与 SymPy 同为可降级依赖）。

## 2. 实测现状（已核查，2026-10）

| 项 | 代码种子 | 本机实例（bolt://localhost:7687 实测） |
|---|---|---|
| 节点数 | 31 | **8** |
| 关系数 | 39 | **9** |
| 标签 | `Concept`/`KnowledgePoint` 等（按代码 schema） | 仅 `Knowledge`（旧 schema） |
| 创建时间 | — | 2026-02-25（早于当前代码版本） |

两个必须承认的问题：

1. **数据与代码不同步**：实例是旧版本写入的，节点/关系数远小于当前种子，且标签 schema 已变更。
   直接复用旧库会得到错误的学习路径；需要重建库或写迁移脚本。
2. **规模决定收益有限**：即使种子全量导入，31 节点的图对"路径规划"也只是演示级。
   真正发挥图优势需要持续灌入更多概念与依赖关系（教研成本）。

## 3. 取舍论证

### 3.1 为什么当初选 Neo4j（而不是继续用 MongoDB 内嵌文档）

| 需求 | MongoDB 文档 | Neo4j 图 |
|---|---|---|
| 概念本身的 CRUD | ✅ 天然适合 | 可以但非所长 |
| "X 的前置知识（递归多层）" | ❌ 需多次往返 + 应用层拼接，层数不定 | ✅ Cypher 可变长路径一条查询 |
| 最短学习路径（概念 A → B） | ❌ 应用层 Dijkstra | ✅ 内置图算法 |
| 变更频率 | 低频 | 低频（图谱本身稳定） |

核心判断：**"前置依赖"是多对多、递归、可变深度的关系**，文档模型表达费劲，
图模型是一等公民。这个判断在概念数量增长后依然成立。

### 3.2 为什么可以"保留但不依赖"

- 31 概念规模的图，内存 Map + 邻接表与 Neo4j 在功能上等价（`getDefaultMathConcepts` 就是证明）；
- 解题核心链路（solver → SymPy）**完全不经过** Neo4j，它只影响 planner 的上下文丰富度与路径规划；
- 降级链路已被自检覆盖（Neo4j 停掉时系统照常工作，内存 fallback 日志可见）。

### 3.3 什么情况下应该放弃 Neo4j

- 概念规模长期停在几十量级、且无教研投入扩图的预期；
- 运维成本敏感（多一个状态ful组件 = 多一份备份/升级/排障面）。

届时删除成本也低：消费方只有 `KnowledgeService` 一个出口，把实现换成内存版即可。

## 4. 当前建议（按优先级）

1. **P1：重建实例数据**——`docker compose down -v` 后重启让种子全量重建，消除旧 schema 残留；
   或在 `waitForNeo4jAndInit` 里加版本号校验（schemaVersion 不匹配则清空重建）。
2. **P2：导入口径统一**——`KnowledgeService` 写入与种子使用同一套 schema，避免再次出现标签漂移。
3. **P2：扩图靠数据集驱动**——从 `datasets/` 题库的知识点字段抽取概念与依赖，半自动扩图，
   而不是手工维护。
4. **持续：保持"可降级"契约**——任何新消费方都必须接受内存 fallback 语义，
   不得把 Neo4j 查询放进关键路径（`/health/ready` 不查它是有意为之）。

## 5. 一句话结论

Neo4j 在此系统中是**"为规模预留的表达能力"而非"当前必需的存储"**：
选型理由（递归前置依赖）成立，降级设计让它零风险保留；当前最大问题不是选错，
而是**实例数据与代码不同步**，重建即可解决。
