4. **登录页在 `console.log` 打印明文密码**——第一轮审阅未发现的凭据泄露点，本轮修复。

## 二、本轮实施的调整与取舍理由

### 调整 1：动手前先建立 git 版本控制基线

- **做法**：`git init` + 提交当前干净状态（399 个文件，`node_modules`/`venv`/日志正确排除），所有后续改动基于可 diff、可回滚的基线。
- **理由**：原方案遗漏了这一前置条件。没有它，本轮 19 个文件的修改 + 12 个新文件一旦出错无法回退。

### 调整 2：密钥治理改为"工具化 + 门禁"，而非一次性手工清理

- **做法**：
  - 新增 `scripts/secret-scan.cjs`（`--scan` / `--redact` 两种模式），检出 3 组真实密钥并完成脱敏，复扫归零；挂入 `npm run secret:scan` 作为提交前/CI 门禁。
  - 新增后端运行期脱敏 `common/utils/redact.ts`，对 axios 错误对象只提取 `status/code/message`，绝不序列化 `config.headers`；替换全部"整体打印错误对象"的日志点（`agents.service.ts`、`agent.base.ts`、`ai-solver.service.ts`、`recovery.service.ts`、`health.controller.ts` 等）。
  - 扫描器明确**豁免 `.env`**（密钥本就该在那里，脱敏会直接破坏本地环境）并排除 `configService.get('JWT_SECRET')` 这类代码误报。
- **取舍理由**：手工改几行只能解决当下，日志打印通道不堵住，下次调试还会再泄露。工具化的代价是一次性写扫描器，收益是"永不复发 + CI 可守门"。
- **仍需人工执行的一步**：3 组已泄露密钥必须在服务商后台**轮换作废**——脱敏只防止继续扩散，已泄露的密钥永远视为已失陷。

### 调整 3：JWT 短时效与前端 401 自动刷新作为一个整体交付

- **做法（后端）**：
  - `TokenService`：access token 15min（`JWT_EXPIRATION`），refresh token 30d（`JWT_REFRESH_TTL_SECONDS`），**只存 SHA-256 哈希**，每次使用即轮换，旧值重放 → 吊销整个令牌族（重用检测）；`/auth/refresh`、`/auth/logout`（`auth.controller.ts`）。
  - `LoginThrottleService`：按用户名+IP 失败计数，5 次失败锁 15 分钟，复用现有 `RedisCacheService`（内存降级），不引入新依赖。
  - 登录接口接入锁定/计数/重置（`user.controller.ts`）。
- **做法（前端，uniapp）**：
  - `request.ts`：401 时**单飞（single-flight）**调用 `/auth/refresh`，成功后重放原请求；并发请求共享同一个刷新 Promise，避免并发刷新互相使对方的新 token 失效（轮换机制下这是真实风险）；4xx 不重试、网络错误提示离线。
  - `stores/user.ts`：refresh token 持久化、`logout` 调用后端吊销。
  - 登录页：保存 refresh token；**删除打印明文密码的 `console.log`**。
- **取舍理由**：原方案只列后端任务。若只改后端，15 分钟过期会让用户反复掉线——安全措施反而制造故障。单飞刷新是 refresh 轮换机制的必备配套，二者必须同时上线。

### 调整 4：错误体系与既有信封兼容，而不是推翻重写

- **做法**：错误输出 `{code, message, traceId}`（`common/errors/*` + `global-exception.filter.ts` + `trace-id.interceptor.ts`），`code` 复用前端已认识的字段位（`error.response.data.message` 仍可读），生产环境不回传堆栈；前端按 4xx 不重试、5xx 由调用方决定是否重试。
- **理由**：前端已有解析逻辑依赖 `data.message`，重写信封会连带改动所有页面，风险大于收益。
