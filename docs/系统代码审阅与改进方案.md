# 高等数学智能教育系统 — 代码审阅与改进方案

> 审阅日期：2026-09-29
> 审阅范围：`nestjs-backend`（主后端）、`uniapp-frontend`（主前端）、`math-tutor-prototype`（React 原型）、
> `python-sympy-service` / `sympy-service`（符号计算）、`formula-renderer-service`、`datasets`、`docker-compose.yml`
> 审阅性质：**只做问题定位与改进方案设计，未改动任何业务代码**

## 0. 审阅概览与总体结论

### 0.1 代码规模画像

| 模块 | 规模 | 状态判断 |
|------|------|----------|
| nestjs-backend | ~150 个 TS 文件，agents 模块单文件最大 1486 行 / rule-engine 1074 行 / orchestrator 890 行 | 骨架完整，核心数学能力弱 |
| uniapp-frontend | 8 个页面 + 16 个组件，solver 页 1885 行 | 功能面铺得广，深度不足 |

### 0.2 总体结论

系统的**工程骨架（分层、DI、DTO 校验、Swagger、健康检查、Docker 编排）已经搭起来了，但"数学教育"这个内核是空的或不可靠的**，具体表现为三个层次的问题：

1. **正确性不可信**：本地规则引擎用正则 + 字符串匹配"猜"答案，猜不到就返回占位符（`（极限值）`、`（方程的解）`）当作最终答案呈现给学生；ε-δ、凹凸性、级数收敛域、ODE 求解等处存在**可复现的数学错误**。
2. **安全性存在 P0 级缺口**：真实 API Key 已明文进入仓库与日志；注册接口存在**管理员权限提升**；生产环境 CORS 可能全放行；SymPy 服务无沙箱、无超时，可被单个请求打挂。
3. **可维护性债务沉重**：两套前端、两份 SymPy 服务、三套公式渲染实现、多个空目录与未使用依赖，架构文档（综合报告）与代码实现严重不符。

> 建议的整体定位：**先止血（P0 安全）→ 再正骨（数学内核重建）→ 后整形（结构/性能/测试）**。详细路线见第 9 章。

## 1. P0 — 必须立即处理（安全 / 数据资产）

### 1.1 真实密钥已明文进入仓库与日志 🔴

**定位**
- `docs/deployment-check-report.md:86` — `KATCODER_API_KEY=sk-…` 完整密钥明文
- `test-api.ps1:2` — 硬编码 `Bearer sk-…`
- `backend-out.log:2418 / 2499 / 2856 / 2913 / 2983` — 日志打印了完整的 `Authorization: Bearer sk-…` 请求头（axios 错误对象被整体序列化）

**风险**：密钥已可被任何拿到仓库/日志的人直接使用，产生真实账单与滥用。日志文件还会随项目分发/备份持续扩散。

**改进方案**
1. **立即轮换**上述所有密钥（SiliconFlow / SimpleTex 等），旧密钥作废——这是第一步，不是最后一步。
2. 清理历史：用 `git filter-repo` / BFG 从 Git 历史中清除密钥；至少删除日志文件中的明文并加入 `.gitignore`。
3. 日志脱敏：封装一个 HTTP 客户端拦截器，在 `error` 序列化前剥离 `Authorization`、`api-key`、`cookie` 等头；禁止 `this.logger.error(error)` 直接打印 axios 错误对象，只允许打印 `error.message` 与状态码。
4. 防再犯：接入 pre-commit 密钥扫描（gitleaks / trufflehog），CI 加一步门禁；`docs/` 中的配置示例一律写成 `KATCODER_API_KEY=<your-key-here>`。
5. `test-api.ps1` 等调试脚本改为从环境变量读取，或直接移出仓库。

### 1.2 管理员权限提升（注册接口） 🔴

**定位**：`nestjs-backend/src/modules/user/user.service.ts:18`

```ts
roles: createUserDto.username === 'admin' ? ['admin'] : ['student'],
```

配合 `user.controller.ts:43-55`（`@Public() @Post('register')`），**任何人以用户名 `admin` 注册即可获得管理员角色**，随后可调用 `GET /user/list`、`POST /user/create`、`DELETE /user/delete/:username`。

**改进方案**
1. 删除"用户名决定角色"的逻辑。注册接口强制写入 `roles: ['student']`，DTO 中用 `forbidNonWhitelisted` 拒绝任何 `roles` 字段（`CreateUserDto` 目前只有 username/password，但没有显式禁止，建议加 `@IsOptional()` 白名单说明或直接不接收）。
2. 角色分配只走管理员接口（`POST /user/create` 带 `@Roles('admin')`），且显式传入 role 并做枚举校验。
3. 保留用户名黑名单（admin / root / system / administrator），避免仿冒。
4. 补一条集成测试：注册 `admin` → 断言 token 中 roles 仅为 student → 访问 `/user/list` 期望 403。

### 1.3 生产环境 CORS 可能全放行 🔴

**定位**：`nestjs-backend/src/main.ts:45-56`

```ts
if (!origin || corsOrigin.length === 0) { callback(null, true); return; }
```

生产环境下若忘记配置 `CORS_ORIGIN`，`corsOrigin` 为 `[]`，**所有来源都被反射放行，且 `credentials: true`** —— 等价于"任意站点可携带用户 Cookie/Token 访问 API"。

**改进方案**
1. 生产模式（`NODE_ENV === 'production'`）下**必须**显式配置 `CORS_ORIGIN`，缺失则启动失败（纳入启动期 env 校验）。
2. 生产分支不再走 `callback(null, true)` 兜底；未命中白名单时应 `callback(new Error(...))`，且不输出具体 origin 到响应体。
3. 把 CORS 白名单、可信代理（`trust proxy`）配置化，并在 Nginx/网关层再设一道。

### 1.4 SymPy 服务：无沙箱、无超时、无复杂度上限 🔴

**定位**：`python-sympy-service/main.py:72-82`（`safe_sympify`）、`:112`、`:187` 等所有端点；服务监听 `0.0.0.0:8000` 且**无鉴权**。

**风险**
- `parse_expr` 未限制 `global_dict`/`local_dict`，表达式可触达 SymPy 命名空间内的可调用对象；历史上有多起 SymPy 解析相关的沙箱逃逸 CVE，缺乏白名单即暴露面。
- `simplify / integrate / limit / dsolve` 均为**可能无限耗时**的操作，没有超时、没有表达式长度/节点数上限、没有 worker 隔离：一个 `integrate(exp(x**100), x)` 之类的请求即可占满 Uvicorn 单线程。
- 服务无任何鉴权与限流，任何能访问 8000 端口的人都可调用。

**改进方案**
1. **解析白名单**：`parse_expr(expr, global_dict={'Symbol': Symbol, 'Integer': Integer, ...仅数学函数}, local_dict={...})`，或使用 `sympy.parsing` 的 `auto_symbol` + 自定义 `TokenError` 处理；禁止函数调用以外的语法（属性访问 `__`、lambda、comprehension）。
2. **复杂度预算**：解析后计算表达式树节点数 / 深度 / 幂次上界，超限直接返回 400；对字符串长度设上限（如 512 字符）。
3. **执行超时**：用 `signal.alarm`（Linux）+ `multiprocessing` 子进程 或 `concurrent.futures.ProcessPoolExecutor(timeout=)` 跑计算，超时即杀；配合 `--workers` 与 `uvicorn --limit-concurrency`，并设置请求级 `timeout_keep_alive`。
4. **服务鉴权**：仅在容器网络内暴露（compose 中**不要** `ports: 8000:8000` 对外），并加内部共享密钥 Header（`X-Internal-Token`）。
5. **降级**：SymPy 不可用时后端已有本地规则，但要保证"规则结果"明确标注置信度为低、并提示"符号计算服务暂不可用"，而不是把占位符当答案。

### 1.5 注册竞态与登录校验绕过面 🔴

**定位**：`user.controller.ts:49-53`（先查后写）、`:62`（`loginDto` 使用内联类型）

**问题**
- 注册并发下两个请求同时通过"用户名已存在"检查，随后 `username` 唯一索引抛 `E11000`，当前**没有捕获**，用户看到 500 而非 409。
- `login(@Body() loginDto: { username: string; password: string })` 是内联类型字面量，编译后无 class 元数据 → 全局 `ValidationPipe` **跳过校验**；若前端传 `{}`，`findOne({ username: undefined })` 在 Mongoose 中会**忽略该条件而返回集合中第一个用户**，构成逻辑绕过面。

**改进方案**
1. 建立 `LoginDto`（`@IsString() @IsNotEmpty() @MinLength(6)`），登录/注册统一走 DTO。
2. 注册改为**原子化**：直接 `create()` 并捕获 `code === 11000` 映射为 `ConflictException`；或在 `username` 上依赖唯一索引 + upsert 语义。
3. 登录接口加**专项限流**（如 10 次/分钟/IP + 5 次/分钟/账号）与失败计数锁定，当前只有全局 100 次/分钟的 IP 限流。
4. 所有鉴权失败返回统一文案（不区分"用户不存在/密码错误"），避免用户枚举。

## 2. 数学正确性 —— 系统核心竞争力所在

> 这是本次审阅中问题最密集的部分。以下每条都给出**可复现的现象**与**改进算法/方案**。

### 2.1 ε-δ 模块：三处数学缺陷 + 一处性能陷阱

**定位**：`uniapp-frontend/src/utils/math/epsilonDelta.ts:50-83`，前端 `components/scenarios/EpsilonDelta.vue:101-108`

**缺陷 A：采样区间包含端点，会把"正确 δ"判为错误**
`checkDelta` 在闭区间 `[x₀-δ, x₀+δ]` 上取样，而 ε-δ 定义要求的是去心邻域 `0 < |x-x₀| < δ`。在端点 `|x-x₀| = δ` 处函数值完全可以超出 ε 带（例如 `x³` 在 `x₀=1`、δ 较大时），导致系统拒绝一个**合法**的 δ，与学生手算结论冲突。

**缺陷 B：跳过阈值是绝对量，小 δ 时"恒成立"**
`if (Math.abs(x - limitPoint) < 0.0001) continue` —— 当 δ < 1e-4 时**所有采样点都被跳过**，函数直接 `return true`，任意 ε 任意 δ 均判为"满足"。学生把 δ 拖到极小值即可通关。

**缺陷 C：`findOptimalDelta` 既不是二分、也找不到真正的"最优"**
- 注释写"二分搜索"，实现是从 `startDelta` 起**线性递减** 1000 步（`:76`），分辨率固定为 `startDelta/1000`。
- 搜索上界是传入的 `startDelta`，**不可能返回比它更大的值**。
- 若 1000 步内无一满足，循环结束后返回**未经任何验证的 `startDelta`**（`:74, 82`），把一个肯定不成立的 δ 当作"最优 δ"展示。

**缺陷 D（前端用法，教学语义错误）**
`EpsilonDelta.vue:101-108` 调用 `findOptimalDelta(..., startDelta = delta.value)`，即**以当前 δ 为上界向下搜**。结果"最优 δ"永远 ≈ 当前 δ，学生看到的是一个自我印证的数字，完全失去"寻找最大可行 δ"的教学意义。

**缺陷 E（性能）**
单次 `findOptimalDelta` = 1000 × 201 ≈ **20 万次函数求值**，且它被放进 Vue `computed`，滑块每次拖动都同步重算 → 主线程掉帧。

**改进方案**
1. **严格按定义采样**：在 `(0, δ)` 内取点，例如 `|x-x₀| = δ·(i/N)`（i=1..N-1，两侧对称），**永不取端点**；跳过阈值改为相对量 `δ·1e-9`，并显式处理"采样点全被跳过"的退化情况（返回"无法判定"而非 true）。
2. **改用真正的解析/二分混合算法**：
   - 对单调型函数可解析求 δ（如 `|f(x)-L|` 在邻域内单调时取边界解）；
   - 通用情况用**对 δ 的二分搜索**（`checkDelta` 关于 δ 通常具有单调性：δ 越小越容易满足），在 `[δ_lo, δ_hi]` 上二分 30~40 次即可达到 1e-9 精度，计算量从 20 万降到 **约 8000 次**；
   - 搜索上界不再取当前 δ，而是取一个与函数定义域相关的固定上界（或从大往小指数退避），这样才能给出"真正的最大 δ"。
3. **失败要显式**：无解时返回 `null` 并在 UI 显示"当前 ε 下未找到可行 δ"，而不是回填 startDelta。
4. **计算移出渲染路径**：改为 `watch` + 防抖（100~150ms）或 Web Worker；结果按 `(fnId, ε)` 做 memo 缓存。
5. **教学增强**：采样法本身就是近似，应在 UI 上标注"数值验证（N=200 采样）"，并补充"符号验证"通道（把 δ 代回 SymPy 求 `|f(x)-L|` 上确界），两者结论不一致时给出提示——这本身就是一个很好的教学点。

### 2.2 导数模块：除零、定义域与术语错误

**定位**：`uniapp-frontend/src/utils/math/derivative.ts`

- **`computeSecantLine`（:44）**：`h` 为 0 时 `(f(x₀+h)-f(x₀))/h` → `0/0 = NaN`，割线整条变成 NaN，图表直接崩。`h` 由滑块驱动，完全可能取到 0。
- **定义域未处理**：`ln(x)` 在 `x₀+h ≤ 0` 时返回 NaN（`:14` 已做定义域保护，但割线、切线未做），NaN 会污染 ECharts 序列。
- **`getConcavityLabel`（:57-63）术语与数学双重问题**：
  - `f''(x₀) = 0` 直接返回"拐点"——**错误**。`f''(x₀)=0` 是拐点的**必要非充分**条件，反例 `f(x)=x⁴` 在 `x=0` 处 `f''=0` 但不是拐点。正确判据是 `f''` 在 `x₀` **两侧变号**（或最低阶非零导数阶数为奇数）。
  - 中文表述自相矛盾：`'凹（上凸）'` / `'凸（下凸）'`。同济版教材约定 `f''>0` 为**凹**，`f''<0` 为**凸**，"上凸/下凸"是另一套（且方向相反）的民间说法，两个体系并列会让学生混乱。

**改进方案**
1. `h` 做下限钳制（如 `|h| ≥ 1e-6`），并在 UI 上把 0 显示为极限符号而非数值；对 `f(x₀±h)` 先做定义域检查，越界时禁用割线并提示。
2. 凹凸性判定改为**符号变化检测**：在 `[x₀-η, x₀]` 与 `[x₀, x₀+η]` 两端各取若干点判 `f''` 符号，同号→凹/凸，异号→拐点，无法判定→"需进一步分析"。
3. 统一术语：全站只用"凹（f''>0）/ 凸（f''<0）"，配一个术语表常量集中管理，避免散落硬编码。
4. 补充数值求导的**误差可视化**：展示 `(f(x₀+h)-f(x₀))/h` 与中心差分 `(f(x₀+h)-f(x₀-h))/(2h)` 的对比及截断误差阶，这是数值分析的重要教学点（目前完全没有中心差分）。

### 2.3 黎曼和 / 积分：缺参数校验、缺方法、缺"真值"兜底

**定位**：`uniapp-frontend/src/utils/math/integral.ts`

- **无入参校验**：`b < a` 时 `dx < 0`，结果符号翻转且矩形宽度为负（图形错乱）；`n ≤ 0` 时 `dx = Infinity`，`sum` 变 NaN。
- **方法单一**：只有左/右/中点，缺**梯形法**与**辛普森法**——这两者是"误差阶对比"教学的核心（左/右/中点 O(1/n)，梯形 O(1/n²)，辛普森 O(1/n⁴)），缺失后"误差随 n 收敛"的观察维度少了一半。
- **精确值依赖人工录入的原函数**（`antideriv` 硬编码 4 个），一旦新增函数就必须改代码；若原函数写错，误差分析全错且无感知。
- **无数值真值兜底**：没有原函数时无法给出误差。

**改进方案**
1. 入口加前置校验：`b > a`、`n` 为 1..1000 的整数、被积函数在区间内可求值（NaN 检测并高亮）。
2. 增加 `trapezoid` 与 `simpson`（辛普森要求 n 为偶数，需自动向上取偶数并处理），四种方法并列展示**误差阶曲线**（log-log 图），这才是黎曼和教学的完整形态。
3. 精确值改为**双通道**：优先调用 SymPy `/integral` 求符号解；失败时用高精度数值积分（如自适应 Gauss-Kronrod / `scipy.integrate.quad`）作为参考真值，并标注"符号解 / 高精度数值参考"。
4. 增加**自适应积分**演示（递归二分 + 误差估计），可作为"为什么黎曼和效率低"的自然延伸。

### 2.4 级数：硬编码系数、无收敛域、无余项

**定位**：`uniapp-frontend/src/utils/math/series.ts`

- **系数硬编码 11 项**（`:8-13`），`taylorApprox` 在 `terms > coeffs.length` 时**静默截断**（`:23`）：学生把项数滑到 15，图像却停在 11 项，且没有任何提示。
- **无收敛域校验**：`ln(1+x)` 级数仅在 `|x| ≤ 1, x ≠ -1` 收敛，但 `computeErrorDistribution` 会在给定 `xRange` 上无差别计算"误差"，在发散区画出来的误差曲线是**无意义的**（甚至因 `Math.pow` 溢出成 Infinity 被 `isFinite` 过滤后曲线断裂）。
- **无余项/误差界**：只画了实测误差，没有拉格朗日余项 `|R_n| ≤ M|x-a|^(n+1)/(n+1)!` 的理论上界，教学上少了一半。
- **Gibbs 现象只在文档里提到（`高等数学系统工程综合报告.md:689-695`），代码中没有任何超调量测量**。
- `factorial`（:15）导出但未被使用（死代码）。

**改进方案**
1. Taylor 系数改为**按函数动态生成**：用 SymPy `/series` 拿系数，或本地维护"导数递推表"，支持任意项数；项数超出可用范围时在 UI 明确提示"当前函数仅支持 N 项"。
2. 引入**收敛域（收敛半径）计算**：比值法/根值法求 R，画误差图时用收敛半径裁剪 x 轴，发散区用灰色遮罩并标注"级数在此发散"。
3. 增加**余项上界曲线**与实测误差曲线叠加对比。
4. Fourier 部分增加 **Gibbs 超调量实时测量**（在跳变点附近求局部极大值与跳变幅度之比，理论极限 ≈ 8.95%），把文档里的知识点变成可观测现象。

### 2.5 知识图谱路径：有向关系被当成无向图

**定位**：`uniapp-frontend/src/utils/math/graph.ts:25-53`

```ts
adj[e.source].push(e.target);
adj[e.target].push(e.source);   // 无向化
```

**问题**：知识图谱的 `PREREQUISITE`（前置依赖）本质是**有向**关系。无向化后，从"定积分"到"极限"的"学习路径"可能沿着**反向的前置边**走，得出"先学定积分再学极限"的建议——对学习者是误导。此外：
- 无权 BFS 忽略节点掌握度、难度、学习成本，无法做真正的个性化路径；
- `queue.shift()` 是 O(n) 操作；
- 无路径与"未找到路径"都返回 `[]`，调用方无法区分（应返回 `null` 或带状态的对象）；
- `getMasteryColor/Label`（:55-69）用 `>= 90` 的百分制阈值，而 `stores/cognitive.ts` 的认知维度是 **0~1** 小数，量纲不一致会导致掌握度一直显示"未学习/红"。

**改进方案**
1. 按**关系类型**决定可遍历方向：`PREREQUISITE` 只允许 `target → source`（先修在前），`RELATED` 可双向。构建邻接表时传入边类型。
2. 学习路径改用**带权最短路（Dijkstra / A*）**，权重 = `f(1-掌握度, 难度, 未学习前置数)`；或采用**拓扑排序 + 分层推荐**：先输出目标节点的所有前置闭包，按拓扑序排列，再在其中优先推荐"掌握度低且前置已满足"的节点——这比最短路更符合教学逻辑。
3. 增加**路径可达性校验**：前置闭包中存在未掌握节点时，路径应显式包含它们。
4. 统一掌握度量纲：全系统约定 **0~1**（或统一 0~100）并提供转换工具函数，用 TypeScript 的**品牌类型**（`type Mastery01 = number & { __brand: 'Mastery01' }`）在编译期阻止混用。
5. `queue.shift()` 改为双端队列/索引指针。

### 2.6 后端规则引擎（LocalComputationService）：模板化"伪解题"

**定位**：`nestjs-backend/src/modules/agents/local-computation/local-computation.service.ts`（1486 行）

这是降级通道，但在 AI 不可用时它就是**唯一**答案来源，问题严重：

**(1) 未计算的占位步骤被当作解题过程**（`:162-208`）
步骤 1~3 的 `result` 是硬编码文案：`'已识别极限类型'`、`'已确定不定式类型'`、`'已应用求解方法'`。系统**从未真正判断过不定式类型**，却在步骤 2 声明"已确定"，并在 `highlight` 里写"只有不定式才能使用洛必达法则"——这是在**用断言冒充推理**。

**(2) 占位符直接作为最终答案**
`computeLimitResult` 兜底返回 `result: '（极限值）'`（`:985`）、`computeEquationResult` 返回 `'（方程的解）'`（`:1041`）、`computeIntegralResult` 返回 `'（积分结果 + C）'`（`:935`）。这些字符串会经过 `finalAnswer` → 前端 → 呈现给学生。

**(3) 分类器脆弱**（`:126-155`）
- `lowerProblem.includes('ode')` 会命中 **`code`、`model`、`node`、`mode`** 等任意含 "ode" 的英文单词；
- 判定顺序里 `EQUATION` 用 `includes('=')`，且排在 `SERIES` 之前 → **含等号的级数题被判成方程**；
- `switch`（`:74-93`）**没有 SERIES / PROOF / GEOMETRY 分支**，这三类被识别出来后落到 `solveGeneralProblem`（`:601`），同样是四步占位模板。

**(4) 方程求解有可复现的错误**（`:990-1044`）
- 用 `parseInt` 解析系数 → **小数系数被截断**：`0.5x²+...` 中 `parseInt('0.5') = 0` → `a = 0` → 除以零 → `Infinity`；
- 隐式系数 1 崩溃：`x²+x=0` 匹配 `[+-]\s*\d*` 得到 `"+"`，`parseInt('+') = NaN` → `disc = NaN` → `disc >= 0` 为 false → 输出 **"无实数解 (Δ = NaN < 0)"**（一个明显错误的答案）；
- 二次正则要求 `x^2` 字面量，不支持 `x²`（Unicode）、不支持 RHS≠0（`2x²+3x=5`）、不支持省项（`x²-4=0`）。

**(5) ODE 覆盖率极低且精度丢失**（`:515-580`）
- 正则只认 `y'' ± a y' ± b y = 0`（首项系数必须为 1）：`2y''-3y'+y=0`、`y''-4y=0`（无 y' 项）、`y''+y=x`（非齐次）、项序不同的写法**全部落到"无法自动提取"**；
- 特征根用 `toFixed(6)` 转浮点（`:541`）：`y''+y'-y=0` 的根应为 `(−1±√5)/2`，系统给出 `-1.618034` / `0.618034`，**丢失精确形式**——数学教育产品给近似值代替精确值是硬伤；
- 复根分支 `generate_ode_steps` 对应的步骤生成（Python 侧 `:467-487`）**只处理两个实根**，复根/重根时步骤缺失。

**(6) 解析器能力过窄**（`:667-720`）
`parsePolynomial` 的 tokenizer 是 `/[+-]?[^+-]+/g`，遇到 `(x^2-1)`、`3*x`、`x^-1` 全部失败并**静默返回 null**，随后降级到三角/指数的字符串硬匹配（`lower.includes('sin')` 之类），_chain 极易给出错误结果。分数还原 `toFractionParts` 只枚举分母 2~12（`:726`），`1/13` 之类直接退化成小数。

**改进方案（这是本次最重要的架构建议）**

> **用"表达式 AST + 规则库"替换"正则 + 字符串匹配"。**

1. 引入**数学表达式解析器**（TypeScript 侧可用 `mathjs`；或直接复用来 SymPy 的 `srepr`/AST JSON），把题目解析成 AST，在 AST 上做模式匹配与变换。这样 `(x+1)/(x-1)`、`x²`、`3*x`、`x^-1` 都能统一处理，正则带来的 90% 缺陷自然消失。
2. **精确有理数运算**：自实现一个 `Fraction`（BigInt 分子/分母）类或引入 `fraction.js`，所有多项式系数走有理数，输出 `\frac{1}{3}` 而不是 `0.3333`；ODE 特征根保留 `(-1±√5)/2` 的根式形式（判别式非完全平方时输出根式/复数精确式）。
3. **按"能力"而非"题型"组织求解器**：实现 `SolverStrategy` 接口（`canSolve(ast): boolean` + `solve(ast): Solution`），用**责任链 + 策略模式**注册：多项式求导/积分、有理函数极限、可分离 ODE、常系数线性 ODE（含非齐次待定系数法/变系数）、一元方程（因式分解/求根公式/数值）等；链上无人能解时**明确返回 `Unsolved` 状态**，由上层决定"转 AI"或"告知学生本题需人工解答"，**绝不返回占位符**。
4. **占位符全面下线**：所有 `（极限值）` 之类改为 `null` + `status: 'unsolved'` + `reason`，前端据此显示"本题暂无法自动求解，已转交 AI / 建议请教老师"，并在监控中统计 `unsolved` 率作为核心质量指标。
5. **答案必须自校验**（见 2.8、2.9）。
6. 分类器换成**打分式**：各题型给出关键词/结构特征得分（如"存在 lim 符号 + →" 得 3 分），取最高分且设阈值；低于阈值进 `GENERAL`。同时补上 SERIES / PROOF / GEOMETRY 的求解分支或明确标注"暂不支持"。

### 2.8 答案等价判定缺失（教育产品的核心能力）🔴

**定位**：`nestjs-backend/src/modules/agents/agents.service.ts:95-115`

```ts
const isCorrect = normalizedStudent === normalizedExpected || (数值近似相等)
```

当前判卷本质是**字符串归一化后比较**。以下全部会被判为"错误"：

- `x+1` vs `1+x`
- `1/2` vs `2/4`（数值通道可救，但 `1/2·x` 不行）
- `(x-1)(x+1)` vs `x²-1`
- `sin(x)/cos(x)` vs `tan(x)`
- `√2/2` vs `1/√2`
- `2x + C` vs `2x + C₁`（积分常数命名差异）
- `e^x` vs `exp(x)`

而 `confidence` 是**硬编码的 0.95 / 0.4**（`:112`），并非真实置信度。

**改进方案**：构建 **`AnswerEquivalenceService`**，三级判定：
1. **数值抽样验证**：对含自由变量的表达式，在定义域内随机取 N 个点（含边界附近、特殊点如 0/±1/π），逐点比较 `|a-b| < ε_rel·max(1,|a|)`；全部通过才算等价。需处理定义域不一致（一方 NaN）的情况。
2. **符号验证**：调 SymPy 计算 `simplify(a - b)` 或 `a.equals(b)`，判是否为 0；同时用 `random` _seed 做 `equals` 的数值交叉验证（SymPy 的 `equals` 本身就是数值+符号混合，但要设超时）。
3. **规范形式归一化**：统一 `C/C₁/C₂` → `C`；`exp(x)` ↔ `e^x`；`√` ↔ `^(1/2)`；排序交换律项（`x+1` → 有序形式）。

输出从布尔升级为 `{ verdict: 'correct' | 'equivalent' | 'incorrect' | 'unknown', confidence: number, evidence: string[] }`，`unknown` 时转 LLM 评判并在 UI 标注"需人工确认"。这一项应作为**独立模块 + 独立测试集**优先建设。

### 2.9 解题结果缺乏自校验闭环

**现状**：`diagnostic.agent.ts:273` 的验证是"让 LLM 自己检查自己的答案"，`step-validation.service.ts` 也是规则+LLM 混合，但**没有任何"把答案代回原题验证"的机制**（如方程解代入原式、导数结果用差分数值验证、积分结果求导验证）。

`hallucination-guard.service.ts`（40KB）内置了定理库与常见误用规则，方向正确，但依赖 LLM 自觉引用定理，缺少**强制校验点**。

**改进方案**：引入 **Verifier 模式**，让求解与验证解耦：

- **方程**：把解代回原方程，符号/数值检查残差；
- **求导**：在若干随机点比较 `(f(x+h)-f(x-h))/(2h)` 与解析导数（相对误差 < 1e-5）；
- **积分**：对结果求导，检查是否等于被积函数（微积分基本定理，天然的自校验）；定积分再用数值积分交叉验证；
- **极限**：用双侧趋近序列（`x₀ ± 10^-k`）数值观察收敛值；
- **ODE**：把通解代入原方程验证恒等（SymPy `checkodesol`）。

把验证结果作为 `verificationResults` 的**硬证据**返回，并在前端用"已通过数值/符号双重验证"徽章展示。已有的 `LeanVerificationService`（形式化证明）可作为第三层，但它依赖本地 `lake` 工具链，应在 `/health` 中体现可用性，不可用时明确降级而不是静默跳过。

## 4. 边界情况与异常处理

**已确认的具体缺口：**

| 场景 | 现状 | 建议 |
|------|------|------|
| `h = 0`（导数割线） | `0/0 → NaN`，图表崩溃 | 下限钳制 + UI 提示 |
| `δ < 1e-4`（ε-δ） | 所有采样点被跳过 → 恒判真 | 相对阈值 + 退化检测 |
| `n ≤ 0` / `b < a`（黎曼和） | `dx = Infinity` / 负宽矩形 | 入口校验 |
| `ln(x)`，x≤0 | NaN 污染序列 | 定义域检查 + 序列过滤 |
| 级数发散区 | 误差曲线无意义/断裂 | 收敛半径裁剪 |

## 5. 代码结构与可维护性

### 5.1 巨型文件与职责混杂

超过 800 行的文件：`local-computation.service.ts`(1486)、`rule-engine.templates.ts`(1074)、`knowledge.service.ts`(1206)、`scenario-config.service.ts`(1014)、`agent.orchestrator.ts`(890)、`solver.agent.ts`(1040)、`model-router.service.ts`(922)、`user-profiling.service.ts`(693)、`hallucination-guard.service.ts`(653/40KB)、`error-diagnosis.service.ts`(752)、`dynamic-knowledge-graph.service.ts`(766)、前端 `solver/index.vue`(1885)、`DemoModePage.tsx`(1519)。

其中 `local-computation.service.ts` **一个类里同时做了**：题型分类、表达式解析、多项式微积分、ODE 求解、字符串术语标准化、HTTP 调用 SymPy、步骤模板生成——违反单一职责。

**改进方案**
- 拆分为：`ExpressionParser`（AST）、`PolynomialAlgebra`、`OdeSolver`、`EquationSolver`、`LimitSolver`、`SolutionStepBuilder`、`SymPyGateway`、`ProblemClassifier`；
- 用**策略 + 责任链**组织求解器（见 2.6），新增题型只需注册新策略，不改主流程；
- `rule-engine.templates.ts`(1074 行) 等数据型文件应改为**数据文件（JSON/YAML）+ 加载器**，让非程序员也能维护教学模板。

### 5.2 重复实现（三处明显的重复）

1. **两份 SymPy 服务**：`python-sympy-service/main.py`(543 行) 与 `sympy-service/main.py`(513 行) 已分叉——前者有 `/geometry`、`/analyze`，后者有 `manual_build_ode` 和 `/solve-ode` 别名；`docker-compose.yml` 只构建 `sympy-service`，意味着 python 版的 geometry 端点是**死代码**。
   → 合并为一份，另一份删除；端点差异用版本化 API 兼容。
2. **两套前端**：`uniapp-frontend`(Vue3/UniApp) 与 `math-tutor-prototype`(React) 功能高度重叠（认知仪表盘、知识图谱、ε-δ、错题本…）。
   → 明确主副：保留 uniapp 为主，React 原型移入 `archive/` 或标注为"设计验证原型"。
3. **三套公式渲染**：`FormulaRenderer.vue`、`MathRenderer.vue`、`MpFormulaRenderer.vue` + 后端 `formula-renderer` 模块 + 独立 `formula-renderer-service` + `simpleTex.service.ts`。
   → 收敛为一个组件（H5 用 KaTeX，小程序用 SVG/图片回退），服务端渲染统一到一个服务。

### 5.3 未使用的依赖

`package.json` 中的 `langchain`、`@langchain/core`、`@langchain/openai`、`@huggingface/inference` 在 `src/` 下**零引用**（架构文档声称使用 LangChain 编排）。
→ 删除（减少安装体积与安全扫描噪声），或在真正引入编排时落实；二选一，不要悬空。

### 5.4 命名与实现不符

`ai-models.service.ts` 中：`GPT` provider 实际是 `Qwen/Qwen2.5-72B-Instruct`，`KATCODER` 与 `DEEPSEEK` 都是 `deepseek-ai/DeepSeek-V3`，`HUGGINGFACE` 也是 DeepSeek-V3；`baseUrl` 在代码中硬编码 `https://api.siliconflow.cn/v1`（`:65, 76, 87, 98`）；API Key 还出现跨 provider 复用（`HF_TOKEN || AI_GPT_API_KEY`，`:75, 97`）。

同时 `高等数学系统工程综合报告.md` 声称使用 **GPT5.2 / DeepSeek / KatCoder** 三模型编排——**文档与实现严重背离**。

**改进方案**
- provider 名称改为中性（`MODEL_PLANNER` / `MODEL_SOLVER` / `MODEL_FAST`），或按真实模型命名；
- 模型名、baseUrl、超时、重试全部配置化（`AI_MODEL_PLANNER` 等环境变量），代码只读取不硬编码；

### 5.5 其他结构性问题

- **无数据库迁移**：MongoDB schema 变更全靠代码推断，无 `migrate-mongo` 之类工具，生产环境无法安全演进。
- **配置校验不完整**：`env.validation.ts` 只校验 `JWT_SECRET` 与 `MONGODB_URI`；且 `main.ts:17` 在 `NestFactory.create(AppModule)` **之前**调用，`ConfigModule.forRoot()` 尚未加载 `.env`，导致**只有系统环境变量能用于校验，`.env` 中的值读不到**（配置了 .env 反而启动失败）。
  → 改为用 `@nestjs/config` 的 Joi/Zod schema 在 `ConfigModule.forRoot({ validate })` 中校验，或先手动 `dotenv.config()` 再校验；校验清单补齐 AI key、Neo4j、Redis、SymPy URL、CORS_ORIGIN。
- **缓存策略分裂**：`RedisCacheService` 已存在，但 `agent.orchestrator.ts:712/744` 用的是**进程内 Map** 缓存，多实例部署时缓存不一致且无 TTL 上限。
  → 统一走 Redis（带 TTL 与 key 命名空间），或明确标注"仅单机可用"。
- **健康检查不完善**：`health.controller.ts:173` 硬编码 `http://localhost:8000` 兜底；无 `/ready`（依赖就绪）与 `/live` 分离；AI 模型、Neo4j、Redis 的可用性未体现在健康状态中。
- **仓库卫生**：根目录**没有 `.gitignore`**，而根目录同时存在 `.env`、十余个 `*.log`、`node_modules/`、`Docker-Desktop-Installer.exe`(数百 MB)、`security-report.json`、`.token-tmp`。
  → 补根 `.gitignore`（忽略 `.env`、`*.log`、`node_modules`、`venv`、`dist`、临时脚本），把 `Docker-Desktop-Installer.exe` 等二进制移出仓库。
